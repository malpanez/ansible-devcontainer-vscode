# v2.1.1

Fixes for what went wrong when these images were opened in VS Code, mostly on a fresh machine. The image fixes reach a template when Renovate moves its pin to the v2.1.1 images; until then the templates keep opening the image they pin, v2.0.0 when this was written. The template changes below apply at once.

- Your git name, email and aliases reach the container. The Dev Containers extension copies your `.gitconfig` only when the container's has nothing but `[filter]` and `[safe]` sections, and the images wrote an `[init]` section to `~/.gitconfig`. `init.defaultBranch` now lives in `/etc/gitconfig`.
- Terminals open in bash on every image. The `vscode` account had `/bin/sh` as its login shell everywhere but golang.
- `ssh` is in the terraform, latex and golang images, so `git` reaches `git@` remotes and `terraform init` fetches `git::ssh://` modules. Before: `error: cannot run ssh`.
- The latex template's `postCreateCommand` no longer fails with `PermissionError` on `.lock`, and `go build` and `go get` no longer fail with permission denied in the golang template. Their named volumes were mounted on directories the images did not have, so a new volume came up owned by root.
- On a host whose uid is not 1000, the terraform template's plugin cache is writable. The extension gives `vscode` your uid and changes the owner only of its home, and the cache is outside it.
- `LANG` is `C.UTF-8` on every image, set by its own Dockerfile. terraform, latex and golang had none, so `locale charmap` printed `ANSI_X3.4-1968`; the Python-based images had it only because the python base happens to set it on some digests.
- golang carries `libstdc++`, one of VS Code's prerequisites for Alpine, so the extension no longer tries to install it when it starts.
- base, ansible and ansible-aws no longer carry a world-writable `/tmp/uv-*.lock`.
- base, terraform, terraform-aws and latex move to Debian's fix for CVE-2026-107161 (high) in `libsasl2`. Their v2.1.0 images replayed an older cached `apt` layer.

## Templates

- The latex template no longer has the docker-in-docker feature. Nothing in it used Docker, the feature forced a privileged container, and dockerd never started anyway: its entrypoint runs `sudo`, which has had no rules in these images since July 2026, so the logs showed `sudo: a password is required`. If you want Docker there, copy `features` and `containerUser` from `devcontainers/ansible/devcontainer.dind.json`.
- `devcontainers/ansible/devcontainer.dind.json` now starts dockerd, because it sets `"containerUser": "root"`. Terminals, tasks and lifecycle commands still run as `vscode`, which can reach the daemon through the `docker` group.
- `devcontainer.docker-socket.json`, in ansible and terraform, now gives you a working `docker`. It mounted the host's socket and stopped there: the images have no `docker` CLI, `vscode` was not in the socket's group, and `devcontainer up` reported success anyway. It now uses the `docker-outside-of-docker` feature with `"containerUser": "root"`, so `docker` reaches the host's daemon as `vscode`. Anything running in the container can now take over the host, so keep this profile to code you trust. The first open builds the feature on top of the image and needs `download.docker.com` and `github.com`.
- `docker run -v` in that profile takes paths on the host, not in the container. `devcontainers/ansible/README.md` shows how to mount the workspace.

## Volumes from an earlier image

A root-owned volume that is still empty takes the owner of the image's directory the next time it is mounted, so the volumes that failed heal on their own when you rebuild the container. A volume that already holds files keeps its owner; remove it with `docker volume rm go-mod-cache go-build-cache pre-commit-cache` after removing the container, or change the owner from the host with `docker exec -u 0 <container> chown -R vscode:vscode <path>`.

## Docs

- `devcontainers/ansible/README.md` told you to select a profile by writing `"extends": "../devcontainers/ansible/devcontainer.dind.json"`. The dev container specification has no such property, and `devcontainer up` on such a file fails with `missing one of "image", "dockerFile" or "dockerComposeFile"`. The README now shows how to copy a profile instead.
- `docs/CONTRIBUTING.md`, `docs/DESIGN_DECISIONS.md` and `docs/IMAGE_OPTIMIZATION.md` no longer rely on `sudo` inside the container. To get a root shell, use `docker exec -u 0` from the host.
