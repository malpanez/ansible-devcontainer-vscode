# v2.0.0

v2.0.0 is a breaking release. This page covers what changes for users of the
images and how to adapt.

## `devcontainer-ansible` and `devcontainer-ansible-podman`: ansible-core plus pinned collections

### What changed

- The images install `ansible-core` instead of the `ansible` package. The core
  is the same as in v1.4.0 (2.21.5, and `ansible --version` prints the same
  `ansible [core 2.21.5]` line), but the 92 collections the `ansible` 14.5.0
  package bundled are no longer all there.
- Four of them are baked in, at the versions v1.4.0 shipped, each pinned by
  version and the sha256 of its Galaxy artifact
  ([`devcontainers/ansible/collections.txt`](../../devcontainers/ansible/collections.txt)):

  | Collection | Version |
  |------------|---------|
  | `ansible.posix` | 2.2.2 |
  | `community.docker` | 5.4.0 |
  | `community.general` | 13.5.0 |
  | `community.library_inventory_filtering_v1` | 1.1.5 (a dependency of `community.docker` and `community.general`) |

- The Python libraries `community.docker` imports are installed too:
  `docker`, `requests` and `paramiko`. In v1.4.0 they were missing, so the
  `community.docker` modules built on the Docker SDK (`docker_swarm*`,
  `docker_node*`, `docker_swarm_service`, the `docker_swarm` inventory) failed
  with `Failed to import the required Python library`.
- `netaddr` is no longer installed. No baked-in collection needs it; the
  `ansible.utils` and `ansible.netcommon` filters that do are not baked in
  either (see below).
- The Python layer now holds only what the stack adds to the base image.
  It used to copy the whole `/usr/local/lib` and `/usr/local/bin` over the
  base, which stored the Python standard library, `uv` and the base's
  site-packages a second time.

Sizes, `linux/amd64`, layers compressed as published (zstd level 12).
v1.4.0 is the image on GHCR; v2.0.0 was built locally from this release,
`devcontainer-ansible` on the v2.0.0 `devcontainer-base`:

| Image | Uncompressed | Compressed |
|-------|--------------|------------|
| `devcontainer-ansible` v1.4.0 | 977 MB | 208 MB |
| `devcontainer-ansible` v2.0.0 | 473 MB | 124 MB |
| `devcontainer-ansible-podman` v1.4.0 | 1010 MB | 217 MB |
| `devcontainer-ansible-podman` v2.0.0 | 564 MB | 152 MB |

The layers the ansible stack adds on top of `devcontainer-base` went from
99 MB to 26 MB compressed, which is what a host that already has the base
downloads. The rest of the `devcontainer-ansible` difference, 109 MB to
98 MB, is the base's own change, mostly Debian's Python 3.11 leaving it (see
[v2.0.0-tools.md](v2.0.0-tools.md)). In `devcontainer-ansible-podman`, which
does not build on `devcontainer-base`, the Python layers went from 99 MB to
34 MB and the other layers stayed within a few kilobytes.

### What you lose

Every collection the `ansible` package bundled other than the four above,
among them `kubernetes.core`, `amazon.aws`, `ansible.utils`,
`ansible.netcommon`, `ansible.windows`, `community.crypto`,
`community.mysql`, `community.postgresql`, `community.hashi_vault`,
`community.sops`, `community.vmware`, `community.windows`,
`containers.podman`, `google.cloud`, `azure.azcollection` and
`hetzner.hcloud`.

`kubernetes.core` was the one v1.4.0 shipped that never worked there: its
modules need the `kubernetes` Python library, which v1.4.0 did not install.
Baking both in would have added about 150 MB uncompressed for a
collection most projects do not use.

A playbook or role that uses one of them now fails with
`couldn't resolve module/action '<namespace>.<collection>.<module>'`, and
ansible-lint reports it as `syntax-check[unknown-module]`.

`importlib.metadata.version("ansible")` and `pip show ansible` no longer find
an `ansible` package. Ask for `ansible-core` instead.

`amazon.aws` (and `boto3`) is planned for a separate `-aws` image variant; it
is not part of this release.

### How to get them back

List what your project uses in a `requirements.yml` at the workspace root:

```yaml
collections:
  - name: community.crypto
  - name: amazon.aws
    version: ">=11.0.0"
```

Every template (`default`, `docker-socket`, `dind` and `podman`) runs
`ansible-galaxy collection install -r requirements.yml` when the container is
created, so rebuilding the container is enough. To install without a
rebuild, run the same command yourself:

```bash
ansible-galaxy collection install -r requirements.yml
```

A single collection works the same way:
`ansible-galaxy collection install community.crypto`.

Collections installed this way go to `~/.ansible/collections`, which the
templates keep on a named volume, so they survive rebuilds. They take
precedence over the baked-in ones, so a project can also pin a different
version of `community.general` or any of the other four. If your project's
`ansible.cfg` sets `collections_path`, `ansible-galaxy` installs into the
first path listed there instead; the baked-in collections stay visible
either way.

Some collections need Python libraries the image does not have, for example
`boto3` for `amazon.aws` or `kubernetes` for `kubernetes.core`. `/usr/local`
belongs to root, so install them for the `vscode` user:

```bash
python3 -m pip install --user boto3
```

`kubernetes.core`, as v1.4.0 had it but with its library this time:

```bash
ansible-galaxy collection install "kubernetes.core==6.6.0"
python3 -m pip install --user kubernetes
```

If you depended on the whole bundle and cannot list what you use yet, the
`ansible` package can still be added on top, at the cost of the 444 MB it
brings:

```bash
python3 -m pip install --user "ansible==14.5.0"
```
