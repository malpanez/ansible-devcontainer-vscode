# v2.0.0

v2.0.0 is a breaking release: read what changes before you upgrade.

- Security: CVE-2026-115557 (critical) is fixed in every image by Python 3.14.10.
- The ansible images install `ansible-core` plus 4 pinned collections instead of the 92-collection `ansible` bundle; install any other collection you use yourself, for example from a `requirements.yml`.
- `devcontainer-terraform` no longer ships the AWS CLI; use `devcontainer-terraform-aws` if you need `aws`.
- Debian's yamllint and python3.11 leave `devcontainer-base` (and so the ansible images built on it); yamllint is now the version in `uv.lock`.
- `ensure-precommit` no longer installs pre-commit; it uses the image's, and fails when there is none.
- The terraform, golang and latex images now ship pre-commit and yamllint, so they are larger; Python hook environments are rebuilt once.
- `devcontainer-base` must be built from the repository root: `docker build -f devcontainers/base/Dockerfile .`.
- New images: `devcontainer-terraform-aws` and `devcontainer-ansible-aws`.

## Security

- **CVE-2026-115557 (critical) is fixed in every image by Python 3.14.10**, which adds CPython's `ssl` denylist of known-compromised certificates. `devcontainer-base` moves to `python:3.14.10-slim-bookworm` and `devcontainer-ansible` inherits it; `devcontainer-ansible-podman` moves to a `python:3.14-slim-trixie` digest that ships 3.14.10; the terraform, golang and latex images install 3.14.10 into `/opt/devcontainer-tools/python`. uv moves to 0.13.6 wherever it is pinned.

## Every image: pinned pre-commit and yamllint

The changes to `devcontainer-base`, `devcontainer-terraform`, `devcontainer-golang` and `devcontainer-latex`, and to `ensure-precommit`, which every image ships.

### What changed

Every image now ships `pre-commit` and `yamllint` at the exact versions in `uv.lock`, installed at build time with `--require-hashes --only-binary :all:`, so every package, dependencies included, is checked against the lock's hash.

- **New export.** The `devcontainer-tools` dependency group in `pyproject.toml` (pre-commit, yamllint) is exported to `requirements-devcontainer-tools.txt`. Like the other `requirements*.txt` files it is generated (`uv export --frozen --only-group devcontainer-tools`), never edited by hand, and regenerated by `renovate-postprocess.yml`. The ansible images keep getting the same versions from `requirements-ansible.txt`.
- **devcontainer-base** installs the export into its system Python (`/usr/local`). Before, it installed `pre-commit==<ARG>` with its dependencies unpinned and unhashed, plus Debian's `yamllint` package. `/usr/bin/python3`, which Debian's yamllint used to bring, is now a link to `/usr/local/bin/python3`.
- **devcontainer-terraform, -golang, -latex** had no pre-commit at all. They now carry a venv at `/opt/devcontainer-tools`, owned by root and read-only to `vscode`, on a CPython installed by the image's pinned uv (3.14.10, the version `devcontainer-base` runs; uv verifies the sha256 of the Python build). 3.14.10 needs uv 0.13.6, the first release that can install it. Only `/usr/local/bin/pre-commit` and `/usr/local/bin/yamllint` are linked onto `PATH`; the interpreter is not, so it does not collide with a Python you install.
- **`ensure-precommit`** (the `postCreateCommand` of every template) no longer installs anything. It used to run `uv tool install pre-commit`, unpinned and unscanned, on every container create of the terraform, golang and latex stacks. Now it uses the image's pre-commit, prints which one, and fails with "this image is broken" when there is none. Copying the stack's `.pre-commit-config.yaml` template, `PRE_COMMIT_HOME`, `pre-commit install -f`, and never running `pre-commit autoupdate` are unchanged.

### Breaking changes

1. **Debian's yamllint is gone from `devcontainer-base`, and so from the ansible images built on it.** In `devcontainer-base`, `yamllint` resolved to Debian's 1.29.0 in `/usr/bin`; it is now the lock's 1.38.0 in `/usr/local/bin`, and a newer yamllint can report findings the old one did not. Debian's `python3.11`, which that package pulled in, went with it (`/usr/bin/python3.11`, `python3-yaml`, `python3-pathspec`, `python3-pkg-resources`). `/usr/bin/python3` stays, as a link to the image's own Python (`/usr/local/bin/python3`, 3.14), so `ansible_python_interpreter: /usr/bin/python3` keeps working and now runs where the Ansible stack is installed. Only something that needed Python 3.11 itself, or Debian's `python3-*` modules, notices.
2. **The terraform, golang and latex images now ship pre-commit and yamllint**, at the lock's version (pre-commit 4.7.0, yamllint 1.38.0 at the time of writing) instead of the newest release at container creation. pre-commit follows `uv.lock`, which Renovate's lock file maintenance moves.
3. **`ensure-precommit` fails when pre-commit is missing.** An image derived from these that deletes pre-commit, or any image without it that runs `ensure-precommit`, now fails its `postCreateCommand` instead of getting an unpinned pre-commit.
4. **A pre-commit left in `~/.local/bin` by the old fallback shadows the image's.** `PATH` puts `~/.local/bin` first on the terraform, golang and latex stacks. Homes are not persisted by the templates, so a new container has none; if yours persists `/home/vscode`, remove it with `uv tool uninstall pre-commit`. `ensure-precommit` prints the path it uses.
5. **Hook environments are rebuilt once.** Python hooks under `PRE_COMMIT_HOME` (`/workspace/.cache/pre-commit`, kept in the workspace) were built on the interpreter the old fallback downloaded into the home directory, which a new container no longer has. pre-commit rebuilds them on the first run; if a hook still fails to start, run `pre-commit clean`.
6. **Larger images.** The terraform, golang and latex images carry an interpreter now (see the sizes below). `devcontainer-base` shrinks.
7. **`devcontainer-base` builds from the repository root.** Its Dockerfile bind-mounts `requirements-devcontainer-tools.txt`, so `docker build devcontainers/base` no longer works; use `docker build -f devcontainers/base/Dockerfile .`, as CI already did everywhere except the publish job, which now does too.
8. **Renovate.** The `ARG PRE_COMMIT_VERSION` in the base Dockerfile and its regex manager are gone; pre-commit moves with `uv.lock`. A new regex manager tracks `ARG TOOLS_PYTHON_VERSION` in the terraform, golang and latex Dockerfiles with the same datasource and depName as the `python:*` base images (`docker`, `python`). That bump stays red until the pinned uv knows the new Python build; bump uv first.

### Image sizes (linux/amd64)

Measured on local builds of the same commit, before and after. *Files* is the image's filesystem (`docker export`), *compressed* is `docker save | gzip`.

| Image | Files before → after | Compressed before → after |
| --- | --- | --- |
| devcontainer-base | 373.6 → 336.9 MB (−36.7) | 142.1 → 130.2 MB (−11.9) |
| devcontainer-terraform | 869.7 → 961.0 MB (+91.3) | 276.2 → 310.6 MB (+34.4) |
| devcontainer-golang | 327.2 → 406.6 MB (+79.4) | 101.6 → 131.3 MB (+29.7) |
| devcontainer-latex | 251.6 → 342.9 MB (+91.3) | 94.6 → 129.0 MB (+34.4) |

The `devcontainer-terraform` row was measured before the AWS CLI left the image, so its "after" is what is now `devcontainer-terraform-aws`. The final `devcontainer-terraform` v2.0.0 is 693.0 MB of files and 239.1 MB compressed (see [the AWS CLI section](#devcontainer-terraform-the-aws-cli-moves-to-devcontainer-terraform-aws)).

Base loses Debian's Python 3.11 with Debian's yamllint. The other three gain `/opt/devcontainer-tools`: the CPython build, without `libpython3.14.so*` (the interpreter is linked statically) and without Tcl/Tk, tkinter, idlelib and turtle, with its standard library compiled to bytecode (76 MB on glibc, 66 MB on musl), and the venv with pre-commit and yamllint (20 MB). The trim saves 47 MB per image on glibc and 35 MB on musl; pip and ensurepip stay in the interpreter. Before, `ensure-precommit` downloaded the newest pre-commit and the newest CPython uv offered into the home directory on every container create: run against the v1 terraform image today, that was CPython 3.15.1 (117 MB) and a 13 MB tool venv, neither pinned nor scanned. That download, and the disk it took in every container, are gone.

### Migration

- Pull or rebuild the images; nothing changes in the templates.
- If you persist the home directory, run `uv tool uninstall pre-commit` once.
- If a Python hook fails after the upgrade, run `pre-commit clean`.
- Build `devcontainer-base` locally with `docker build -f devcontainers/base/Dockerfile .`.

## `devcontainer-ansible` and `devcontainer-ansible-podman`: ansible-core plus pinned collections

### What changed

- The images install `ansible-core` instead of the `ansible` package. The core
  is the same as in v1.4.0 (2.21.5, and `ansible --version` prints the same
  `ansible [core 2.21.5]` line), but the 92 collections the `ansible` 14.5.0
  package bundled are no longer all there.
- Four of them are baked in, at the versions v1.4.0 shipped, each pinned by
  version and the sha256 of its Galaxy artifact
  ([`devcontainers/ansible/collections.txt`](../../devcontainers/ansible/collections.txt)):

  | Collection | Version |
  |------------|---------|
  | `ansible.posix` | 2.2.2 |
  | `community.docker` | 5.4.0 |
  | `community.general` | 13.5.0 |
  | `community.library_inventory_filtering_v1` | 1.1.5 (a dependency of `community.docker` and `community.general`) |

- The Python libraries `community.docker` imports are installed too:
  `docker`, `requests` and `paramiko`. In v1.4.0 they were missing, so the
  `community.docker` modules built on the Docker SDK (`docker_swarm*`,
  `docker_node*`, `docker_swarm_service`, the `docker_swarm` inventory) failed
  with `Failed to import the required Python library`.
- `netaddr` is no longer installed. No baked-in collection needs it; the
  `ansible.utils` and `ansible.netcommon` filters that do are not baked in
  either (see below).
- The Python layer now holds only what the stack adds to the base image.
  It used to copy the whole `/usr/local/lib` and `/usr/local/bin` over the
  base, which stored the Python standard library, `uv` and the base's
  site-packages a second time.

Sizes, `linux/amd64`, layers compressed as published (zstd level 12).
v1.4.0 is the image on GHCR; v2.0.0 was built locally from this release,
`devcontainer-ansible` on the v2.0.0 `devcontainer-base`:

| Image | Uncompressed | Compressed |
|-------|--------------|------------|
| `devcontainer-ansible` v1.4.0 | 977 MB | 208 MB |
| `devcontainer-ansible` v2.0.0 | 473 MB | 124 MB |
| `devcontainer-ansible-podman` v1.4.0 | 1010 MB | 217 MB |
| `devcontainer-ansible-podman` v2.0.0 | 564 MB | 152 MB |

The layers the ansible stack adds on top of `devcontainer-base` went from
99 MB to 26 MB compressed, which is what a host that already has the base
downloads. The rest of the `devcontainer-ansible` difference, 109 MB to
98 MB, is the base's own change, mostly Debian's Python 3.11 leaving it (see
[the tooling section](#every-image-pinned-pre-commit-and-yamllint)). In `devcontainer-ansible-podman`, which
does not build on `devcontainer-base`, the Python layers went from 99 MB to
34 MB and the other layers stayed within a few kilobytes.

### What you lose

Every collection the `ansible` package bundled other than the four above,
among them `kubernetes.core`, `amazon.aws`, `ansible.utils`,
`ansible.netcommon`, `ansible.windows`, `community.crypto`,
`community.mysql`, `community.postgresql`, `community.hashi_vault`,
`community.sops`, `community.vmware`, `community.windows`,
`containers.podman`, `google.cloud`, `azure.azcollection` and
`hetzner.hcloud`.

`kubernetes.core` was the one v1.4.0 shipped that never worked there: its
modules need the `kubernetes` Python library, which v1.4.0 did not install.
Baking both in would have added about 150 MB uncompressed for a
collection most projects do not use.

A playbook or role that uses one of them now fails with
`couldn't resolve module/action '<namespace>.<collection>.<module>'`, and
ansible-lint reports it as `syntax-check[unknown-module]`.

`importlib.metadata.version("ansible")` and `pip show ansible` no longer find
an `ansible` package. Ask for `ansible-core` instead.

`amazon.aws` comes back with `boto3`, `botocore` and the AWS CLI in the new
`devcontainer-ansible-aws` (see [New images](#new-images-devcontainer-terraform-aws-and-devcontainer-ansible-aws)).

### How to get them back

List what your project uses in a `requirements.yml` at the workspace root:

```yaml
collections:
  - name: community.crypto
  - name: amazon.aws
    version: ">=11.0.0"
```

Every template (`default`, `docker-socket`, `dind` and `podman`) runs
`ansible-galaxy collection install -r requirements.yml` when the container is
created, so rebuilding the container is enough. To install without a
rebuild, run the same command yourself:

```bash
ansible-galaxy collection install -r requirements.yml
```

A single collection works the same way:
`ansible-galaxy collection install community.crypto`.

Collections installed this way go to `~/.ansible/collections`, which the
templates keep on a named volume, so they survive rebuilds. They take
precedence over the baked-in ones, so a project can also pin a different
version of `community.general` or any of the other four. If your project's
`ansible.cfg` sets `collections_path`, `ansible-galaxy` installs into the
first path listed there instead; the baked-in collections stay visible
either way.

Some collections need Python libraries the image does not have, for example
`boto3` for `amazon.aws` (or use `devcontainer-ansible-aws`, which has both)
or `kubernetes` for `kubernetes.core`. `/usr/local` belongs to root, so
install them for the `vscode` user:

```bash
python3 -m pip install --user boto3
```

`kubernetes.core`, as v1.4.0 had it but with its library this time:

```bash
ansible-galaxy collection install "kubernetes.core==6.6.0"
python3 -m pip install --user kubernetes
```

If you depended on the whole bundle and cannot list what you use yet, the
`ansible` package can still be added on top, at the cost of the 444 MB it
brings:

```bash
python3 -m pip install --user "ansible==14.5.0"
```

## `devcontainer-terraform`: the AWS CLI moves to `devcontainer-terraform-aws`

### What changed

- `devcontainer-terraform` no longer ships AWS CLI v2: `aws` and
  `aws_completer` are gone from `/usr/local/bin`, and `/usr/local/aws-cli`
  with them.
- The CLI moved, unchanged, to the new `devcontainer-terraform-aws` (below):
  AWS CLI 2.38.5 at the time of writing, from the same AWS download, checked
  against the same pinned sha256.
- Terraform, Terragrunt, TFLint, SOPS, age, uv, pre-commit and yamllint stay
  as they are.

Sizes, `linux/amd64`, both built locally from this release. *Files* is the
image's filesystem (`docker export`), *compressed* is `docker save | gzip -6`:

| Image | Files | Compressed |
|-------|-------|------------|
| `devcontainer-terraform` with the AWS CLI | 961.0 MB | 310.6 MB |
| `devcontainer-terraform` v2.0.0 | 693.0 MB | 239.1 MB |

The AWS CLI was 268 MB of files and 71.5 MB compressed: it bundles its own
Python.

### What you lose

The `aws` command. Terraform's AWS provider does not need it: the provider
has its own SDK and reads the same credentials (environment variables,
`~/.aws/config` and `~/.aws/credentials`). What breaks is whatever runs
`aws` itself, now with `aws: command not found`: `aws sso login` to refresh
an SSO session, `aws configure`, `local-exec` provisioners and `external`
data sources that call it, `credential_process` entries and shell scripts
that use it.

### How to get it back

Use `ghcr.io/malpanez/devcontainer-terraform-aws` instead: the same image
with the AWS CLI on top. In your `devcontainer.json`:

```json
"image": "ghcr.io/malpanez/devcontainer-terraform-aws:v2.0.0"
```

## New images: `devcontainer-terraform-aws` and `devcontainer-ansible-aws`

### What they are

- **`devcontainer-terraform-aws`**: `devcontainer-terraform` plus AWS CLI v2.
- **`devcontainer-ansible-aws`**: `devcontainer-ansible` plus:
  - `amazon.aws` 12.0.0, pinned with the sha256 of its Galaxy artifact in
    [`devcontainers/ansible/collections-aws.txt`](../../devcontainers/ansible/collections-aws.txt)
    and installed like the four collections above;
  - `boto3` and `botocore` 1.43.118 with their dependencies (`s3transfer`,
    `python-dateutil`, `six`), at the versions and hashes of the `aws` group
    of `uv.lock` (exported to `requirements-aws.txt`);
  - AWS CLI v2.

Both are published like every other image: `linux/amd64` and `linux/arm64`,
built and scanned by `build-containers.yml` (`devcontainer-ansible-aws` on
the `devcontainer-base` of the same run), signed, and given the release's
version tag by `release.yml`. Each is a stage of its stack's Dockerfile
(`docker build --target terraform-aws` or `--target ansible-aws`), so it is
always the plain image of the same build plus the AWS layers. The AWS CLI
version and the sha256 of each architecture's download are pinned once, in
`devcontainers/scripts/install-aws-cli.sh`, which both images run; Renovate
bumps it and Renovate Post-Process recomputes the hashes.

Sizes, measured as for `devcontainer-terraform` above (gzip, so not
comparable with the zstd figures of the ansible table):

| Image | Files | Compressed |
|-------|-------|------------|
| `devcontainer-terraform-aws` | 961.0 MB | 310.6 MB |
| `devcontainer-ansible` v2.0.0 | 457.7 MB | 162.4 MB |
| `devcontainer-ansible-aws` | 764.8 MB | 252.6 MB |

On top of the plain image, the AWS CLI adds 71.5 MB compressed and, in
`devcontainer-ansible-aws`, the SDK and `amazon.aws` another 18.7 MB
(`botocore` is 22 MB of files, `amazon.aws` 10 MB).

### Templates come after this release

The dev container templates (`devcontainers/<stack>/devcontainer*.json`) and
the examples open an image pinned to a published release
(`<image>:vX.Y.Z@sha256:...`). The `-aws` images have none before this one,
so no template opens them yet: `-aws` templates follow once v2.0.0 is
published. Until then, set the `image` of your own `devcontainer.json` as
shown above. The examples that mount `~/.aws`
([`docs/INTEGRATION_GUIDE.md`](../INTEGRATION_GUIDE.md) Example 2 and
[`examples/terraform-project`](../../examples/terraform-project)) still pin
`devcontainer-terraform`, which loses the CLI when Renovate moves them to
v2.0.0; they move to `devcontainer-terraform-aws` with the templates.
